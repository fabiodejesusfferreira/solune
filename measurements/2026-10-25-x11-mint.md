## How to read it, and what was not measured

- **System CPU is noisy.** The baseline (7.05 %) came out higher than run b (4.48 %). That doesn't mean the spike lowers CPU use: other programs stayed open the whole time (Claude desktop, Steam/steamwebhelper, Firefox, Zed, rust-analyzer, Cinnamon), and their load varies. The per-process number (utime+stime of the spike's PID) is the reliable one. System CPU only serves as an order of magnitude.
- **intel_gpu_top did not work.** It aborts with `get_num_gts: Assertion '!errno || errno == ENOENT' failed` (exit 134), most likely because it lacks permission for the i915 PMU (`perf_event_paranoid` = 4). I didn't use sudo. I used these instead:
  - `rc6_residency_ms` (gt0): the share of the window the GPU spent in RC6 (deep idle). The "non-RC6" value is 100 − RC6. It covers the whole GPU, including Cinnamon and Xorg.
  - `drm-engine-*` from `/proc/PID/fdinfo` (i915): the busy time of each engine attributed to the spike's DRM clients, divided by the window. "video" is the VCS (decoding). It reads 7.86 % with vaapi and 0 with `--hwdec no`, which confirms hardware decoding.
  - `gt_act_freq_mhz` and `gt_cur_freq_mhz` read once per second. `act` falls to 0 when the GPU is in RC6, which is why the minimum is 0. `cur` is the requested frequency.
- **Dropped frames: not measured.** The spike doesn't report `frame-drop-count`/`vo-drop-frame-count`, and I didn't watch the screen during the runs. The spike printed no errors. The only stray line is `Cannot load libcuda.so.1` (mpv probing CUDA, harmless on Intel). Both runs exited with code 0.
- **Run d skipped:** `mpv` is not installed on the machine (`which mpv` returns nothing).
- **Commit measured: a3803f9.** The working tree had untracked files (`MEMORY.md`, `docs/Solune UI e UX.html`), so I didn't pull. origin/main is at a33effb, two commits ahead. The diff between them only touches `build.rs` (linking against `libmpv.so.2`), CI, README and docs, with no change to the player's runtime code.
- The video is a 6.133 s clip that plays in a loop (`loop-file=inf`), so the 60 s window covers about 10 loops, each with a seek back to the start.
- The display runs at 100 Hz (1920x1080), while the video is about 30 fps.

## Method

Script: `measurements/2026-10-25-measure.py` (a copy of the one I ran). Each run:

```
python3 -I measure.py a-baseline log-a.txt
python3 -I measure.py b-x11-autosafe log-b.txt -- target/release/solune-player-spike /home/dejesus/Vídeos/ruiva.mp4 --surface x11 --seconds 75
python3 -I measure.py c-x11-hwdec-no log-c.txt -- target/release/solune-player-spike /home/dejesus/Vídeos/ruiva.mp4 --surface x11 --seconds 75 --hwdec no
```

with 5 s of pause between them. Each run:

- starts the process and waits 10 s;
- reads utime+stime (fields 14 and 15 of `/proc/PID/stat`), the `cpu` line of `/proc/stat`, `rc6_residency_ms` and the `drm-engine-*` values from `/proc/PID/fdinfo/*` (deduplicated by `drm-client-id`);
- reads `gt_act_freq_mhz` and `gt_cur_freq_mhz` once per second for 60 s;
- reads everything again and also takes `VmRSS` from `/proc/PID/status`.

Process CPU = Δ(utime+stime) / (CLK_TCK × window) × 100. System CPU = (Δtotal − Δ(idle+iowait)) / Δtotal × 100, where total adds the first 8 fields of the `cpu` line, so it is a share of all 4 CPUs. As a side figure it also records the CPU of Xorg and cinnamon (one core) during the window.
